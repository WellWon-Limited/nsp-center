# Разработка NSP Center

Стек: React 19, TypeScript 5, Vite 8, Node.js 22.12+ и npm с package-lock.json.
Проверено на Node 26.13.0 / npm 11.20.0. Основа — статические HTML-документы с
React hydration; бэкенд исходного магазина не используется. Сервер страниц
`apps/web/server.mjs` отдаёт HTML и проксирует `/api/` в отдельный процесс
`apps/api/server.mjs`. Только API подключается к PostgreSQL и внешним интеграциям.

Админка отделена от покупательского сайта: `apps/admin/` — отдельные точка входа,
Vite-сборка и HTTP-сервер. Сайт расположен в `apps/web/`: точка входа,
Vite-конфигурация, сервер и страницы покупателя. Реализации общих компонентов,
стилей и клиентского состояния находятся в `packages/presentation/`.
Общий пакет не импортирует исходники приложений; админка не импортирует сайт.
Они включаются в каждую сборку, а не загружаются с работающего сайта.
Клиентские редакторы админки не входят в покупательскую сборку.

## Установка и запуск

Все команды выполняются из корня репозитория. Локальная PostgreSQL остаётся
прежней: база и её каталог данных не переносятся.

```sh
npm ci
npm run build
```

Четыре процесса (каждый в отдельном терминале; уже запущенную базу повторно не запускать):

```sh
npm run db:local
# После первого запуска базы — в другом терминале:
npm run db:secure
npm run db:migrate
npm run api
npm run preview
npm run admin
```

- PostgreSQL: прежний порт 8700, постоянные данные вне репозитория.
- API: `apps/api/server.mjs`, адрес по умолчанию `127.0.0.1:8701`.
  Только этот процесс читает корневой `.env`, `DATABASE_URL` и ключи интеграций.
  `API_PORT`, `API_HOST` меняют его слушатель; `NSP_LOAD_ENV=0` отключает чтение `.env`.
- Сайт: `apps/web/server.mjs`, адрес `127.0.0.1:5217`.
  Процесс не читает `.env`, не подключается к базе, не импортирует серверные модули.
  `API_ORIGIN` в окружении задаёт адрес API (по умолчанию `http://127.0.0.1:8701`).
  `PORT` и `HOST` также задаются окружением команды.

- Админка: `apps/admin/server.mjs`, адрес по умолчанию `127.0.0.1:5218`.
  Сборка `dist-admin` содержит редакторы, общие компоненты предпросмотра, стили,
  изображения и шрифты. Серверу не нужны `dist`, исходники сайта или доступ к БД.
  `ADMIN_PORT`, `ADMIN_HOST` задают слушатель, `SITE_ORIGIN` — адрес кнопок «Открыть сайт».
  Сайт перенаправляет прежний `/office-k7m4q9/` в `ADMIN_ORIGIN` (по умолчанию
  `http://127.0.0.1:5218`); параметры раздела и товара сохраняются.

Браузер по-прежнему использует `/api/…` на адресе своего приложения. Прокси передаёт cookie,
тело загрузки и публичный Host; вход, защита запросов и адреса файлов сохраняются.
За доверенным HTTPS-прокси задайте веб-процессу `TRUST_PROXY=1`, а внешнему прокси —
перезапись `X-Forwarded-Proto` и `X-Forwarded-For`. Прямой доступ к API при размещении закрывается сетью.
`GET /api/health` проверяет работу процесса и сообщает наличие настройки базы;
это не проверка доступности PostgreSQL.

Для разработки интерфейса вместо `npm run preview` используйте `npm run dev`:
Vite тоже передаёт `/api/` отдельному API. Одновременно dev и preview не запускаются.
Для проверки динамических страниц новых категорий, товаров, статей и HTTP-статусов
используйте preview. Старые адреса, пагинация, sitemap и правила индексирования сохранены.

Перед запуском стенда агенты проверяют реестр Factory: `cv servers ports mine`.
На текущем компьютере роль API в реестре занята PostgreSQL (8700). Поэтому
локальный стенд использует Unix-сокет: отдельный процесс API без дополнительного
сетевого порта. Одинаковое значение `API_SOCKET` задаётся API, сайту и админке:

```sh
API_SOCKET=/tmp/nsp-center-api-v2.sock npm run api
API_SOCKET=/tmp/nsp-center-api-v2.sock npm run preview
API_SOCKET=/tmp/nsp-center-api-v2.sock npm run admin
```

Для Vite используется то же окружение: `API_SOCKET=… npm run dev`.
API создаёт сокет с доступом только владельцу; при штатной остановке Node убирает
его сам. Чужой или оставшийся после аварии сокет автоматически не удаляется.
Переменная имеет приоритет над `API_ORIGIN`. TCP остаётся доступным для раздельных
контейнеров и компьютеров. Интеграционные тесты проверяют оба способа соединения.

Отдельные сборки в монорепозитории:

```sh
npm run build:web
# Для админки без сборки сайта (общие данные и типы нужны обеим сборкам):
npm run content
npm run typecheck
npm run build:admin
```

`npm run build` собирает оба интерфейса. Для разработки админки —
`npm run dev:admin` с тем же `API_SOCKET` или `API_ORIGIN`.
Предпросмотр получает полную исходную карточку и тексты старых страниц через
закрытый для покупателей `/api/admin/preview-data`. Сохранённые данные и
несохранённая форма объединяются в памяти. Покупательская сессия в админке
не восстанавливается и не синхронизируется. Встроенный просмотр не публикует
изменения и не позволяет оформлять заказы.
При изменении общих компонентов надо обновить обе сборки для одинакового вида.

API можно подготовить и запустить без Vite-сборки и `dist`:

```sh
npm run content:catalog
npm run api
```

Полный исходный каталог находится в `packages/catalog/generated/content.json`;
он предназначен для API. `public.json` рядом содержит публичные данные для
сервера страниц. Браузерный summary остаётся в `packages/catalog/generated/`.
Эти файлы производные и не хранятся в Git. Правила без состояния находятся в
`packages/domain/`; адаптеры типов для интерфейсов находятся в `packages/presentation/`.
Авторские тексты, настройки изображений и сведения о товарах — в
`packages/catalog/source/`; они нужны подготовке данных и обоим интерфейсам.

## Полный quality gate

```sh
npm run check
```

Последовательно: offline extraction/import, browser summary, TypeScript,
production build, HTML страниц, service worker, тесты и сверка контента
(9 проверок). Количество тестов и страниц берётся из текущего вывода команды.
Без `NSP_TEST_URL` четыре внешние HTTP-проверки явно пропускаются; отдельный
интеграционный тест повторяет их на изолированной связке web + API + PostgreSQL.

`tests/site-images.test.mjs` проверяет, что изображения в `public/` используются
сайтом или данными каталога. По разрешению владельца удалены 48 неиспользуемых
дизайн-черновиков, вызывавших сбой после контрольной точки `1a885aa`.
Проверка не ослаблена; исходники действующих изображений сохранены.
Сверку контента можно выполнить отдельно: `node scripts/check-content.mjs`.

Для проверки уже запущенного изолированного стенда:

```sh
NSP_TEST_URL=http://127.0.0.1:5217 npm test
```

## Источники и импорт

- `scripts/extract-prototype.mjs` распаковывает только данные prototype bundle:
  шрифты, изображение, CSS tokens и provenance. Bundled JavaScript не исполняется.
- `scripts/import-content.mjs` читает JSON и raw HTML снимка, очищает markup,
  локализует изображения/документы, чинит старые product links. Сеть не нужна.
- `scripts/split-content.mjs` отделяет компактный browser summary от полных
  описаний. Детали текущей страницы встроены в её HTML безопасным JSON.
- `scripts/prerender.mjs` строит все маршруты; цена всегда внутри Product.offers.
- `scripts/check-content.mjs` независимо сверяет источник и импорт: поля,
  семантические тексты, пагинацию, ссылки и bytes/SHA256 локальных ресурсов.

Не редактируйте производные `packages/catalog/generated/` и `public/media/` вручную.
Снимок можно обновить отдельно по `references/nsp-center.ru/README.md`; это
изменение цен/контента требует повторного полного gate.

## CI и публикация

`npm run check` собирает сайт, выполняет тесты и сверку с исходным снимком.
`tests/separate-api.test.mjs` дополнительно запускает API из временного каталога
без `src`, `dist` и `.env`, отдельный сервер страниц и временную PostgreSQL.
Проверяются вход, права, сохранение корзины, загрузка файла, новый товар,
новая категория, sitemap и сохранение сессий после перезапуска API. Внутри этого
теста проверяются все 227 адресов снимка и служебный вход на запущенном сайте.

Dockerfile имеет три независимые цели: `api`, `admin` и `web` (последняя — по умолчанию).
CI собирает обе и проверяет запросы через web к API. `compose.yaml` соединяет
их закрытой сетью; PostgreSQL в состав compose не входит. Для подключения
существующей базы контейнеру задаётся `API_DATABASE_URL` с доступным ему адресом.
Контейнеры web и admin получают адрес API и адрес соседнего интерфейса для ссылок;
секреты задаются только контейнеру API. В compose порты интерфейсов — 5217 и 5218.

Для будущего размещения нужно настроить оба сервиса; прежняя настройка одного
контейнера больше не обеспечивает работу API. Изменения ещё не опубликованы.
Развёртывание и слияние в main выполняются только с разрешения владельца.
На существующем dev-стенде конфигурация в ходе локального разделения не меняется.

## Цены: розничная и по дисконтной карте

Источник — прайс NSP в долларах (у.е. = $), выгруженный в
`references/prices/nsp-2026-11.json` (колонки `dist` — цена по дисконтной карте,
`retail` — розничная). Курс `rubPerUnit` в том же файле — курс склада, он меняется
(94 ₽ за $ с 2026-11-05): новое число в этом поле и пересборка
обновляют все цены. `scripts/pricing.mjs`
пересчитывает цены в рубли при импорте (`product.prices`); товары без строки в
прайсе сохраняют цену снимка и не имеют цены по карте. Исходная цена снимка
(`product.price`) не меняется. Проверка — `tests/build.test.mjs`.

Цена по карте не публичная: дистрибьютор не может
выставлять товар всем по цене дистрибьютора. Страницы, данные в браузере
(`summary.json`) и `/api/site` несут только розничную цену
(`scripts/card-prices.mjs`, `publicProduct`). Цены по карте отдаёт только
`GET /api/card-prices` — вошедшему аккаунту с номером карты в профиле или
администратору; браузер держит их в памяти и не кэширует. Посетитель без входа видит
«Скидка до 30% по дисконтной карте — войдите или оформите карту», без суммы. Без
сервера аккаунтов (локальный режим) цен по карте нет ни у кого. Номер карты пока
не сверяется с базой NSP. Проверки — `tests/card-prices.test.mjs`,
`tests/accounts.test.mjs`.

## Страницы-темы

`/temy/<slug>/` отвечает на один поисковый вопрос («для чего нужен витамин D3») и
ведёт к главному товару и товарам, которые принимают вместе с ним. Каждая тема —
файл `packages/catalog/source/theme-data/<slug>.json` (читает `scripts/themes.mjs`), вёрстка —
`packages/presentation/theme-page.tsx`; на странице главного товара появляется блок «С чем
сочетают». Браузер получает только список тем, полный текст темы встроен в её
страницу, поэтому новые темы не утяжеляют сайт. Тексты опираются на базу лекций врачей (сама
база в репозиторий не кладётся) и не обещают лечения: `tests/themes.test.mjs`
не пропускает такие формулировки и проверяет ссылки, H1 и разметку FAQPage.

## Приложение на телефоне (PWA)

Сайт устанавливается на телефон и компьютер как приложение: `public/manifest.webmanifest`
(название NSP Center, иконки `public/icons/` — листик логотипа на тёмно-зелёном) и
сервис-воркер `dist/sw.js`, который пишет `scripts/pwa.mjs` из `scripts/sw-template.js`
в конце `npm run build`. Он заранее кладёт в кэш JS/CSS, иконки и страницы вкладок
(«Главная», «Каталог», «Консультация», «План», «Профиль», «Корзина»), поэтому план приёма и
марафон (они хранятся в браузере) работают без сети. Страница, которая уже есть в кэше, открывается
сразу из него, а свежая копия скачивается в фоне на следующий раз; новая страница берётся из сети.
`apps/web/src/page-warmup.mjs` заранее просит кэшировать вкладки, разделы каталога и товары на экране (не при
экономии трафика и не на медленной связи) и ссылку в момент касания. Версия сервис-воркера считается
по всем собранным страницам и файлам, поэтому после обновления сайта старые копии заменяются; копии
предыдущей версии живут до следующего обновления. Управление сайтом и API не кэшируются.
Окно «Установите приложение» (`packages/presentation/pwa.tsx`) появляется при каждом входе на сайт и
обновлении страницы, пока приложение не установлено (не при переходах между страницами),
и затемняет экран; та же кнопка есть в профиле. На Android и в Chrome/Edge она сразу
запускает установку, на iPhone показывает шаги «Поделиться → На экран „Домой“». На
телефоне первую страницу визита закрывает экран загрузки с логотипом (`index.html`).
Напоминания о приёме приходят в колокольчик; кнопка «Присылать уведомления» есть только в установленном
приложении (на iPhone сайт в Safari уведомлять не может), уведомления приходят, пока приложение открыто или
свёрнуто; при закрытом приложении нужны push-уведомления с сервера. В приложении на iPhone сайт не копит историю браузера
(`packages/presentation/app-history.mjs`: каждая ссылка заменяет страницу, путь назад хранится в sessionStorage, вкладки начинают его
заново), поэтому системные свайпы iOS назад и вперёд не срабатывают; «назад» — кнопкой или свайпом от левого края
на любом экране с кнопкой «Назад» или «На главную» (в тесте — к предыдущему вопросу), без значков во время
свайпа; где кнопки нет (главная и вкладки, открытые с нижней панели), свайпа нет. Возврат — к месту прокрутки.
Фото сайта сжаты (JPEG), карточки товаров показывают облегчённые копии `public/images/products/web/`.
В репозитории хранятся только картинки, которые показывает сайт: `tests/site-images.test.mjs` не пропустит
картинку в `public/`, которой не пользуется ни одна собранная страница, стиль, скрипт или данные каталога (страницы
вариантов не в счёт; исключение — исходник иконок `public/icons/app-icon.svg`). Снимок старого сайта
`references/nsp-center.ru/` остаётся: из него собирается каталог и сверяются фото товаров.
Проверка — `tests/build.test.mjs`.

## Пробный аккаунт

### Лист ожидания и баллы (локальная версия)

Кнопка «Сообщить о поступлении» в каталоге и на странице отсутствующего товара
сохраняет его в `LocalState.waitlist`. В кабинете список расположен рядом с
избранным. После загрузки обновлённого каталога подтверждённый `InStock` создаёт
одно уведомление в колокольчике; повторная загрузка не дублирует его. Новый
цикл `OutOfStock` → `InStock` снова уведомляет. Проверка — `tests/waitlist.test.mjs`.
Это не подключение к складу и не фоновый push: изменения доступны после
обновления каталога и открытия приложения, данные хранятся в этом браузере.

`LoyaltyStatus` показывает место для баланса на карте и в корзине владельца
карты, а также заданный владельцем порог 100 баллов. Баланс, курс обмена,
лимит оплаты и источник данных ещё не согласованы. Поэтому баланс неизвестен,
списание недоступно, итог заказа не уменьшается и фиктивные баллы не начисляются.

Без базы данных (нет `DATABASE_URL`) профиль хранится в браузере (`apps/web/src/auth.tsx`). Чтобы посмотреть
личный кабинет, войдите как `demo@nsp-center.ru` с паролем `demo2026`: в этот браузер
кладётся готовый аккаунт «Анна Демо» с дисконтной картой (он заменяет локальный аккаунт,
если тот был). Гость видит на главной «Ваш план» и приглашение зарегистрироваться; по имени
сайт обращается только к вошедшему.

## Карта пунктов СДЭК на оформлении заказа

На странице `/checkout/` при выборе «СДЭК по России» покупатель выбирает пункт выдачи или постамат на карте СДЭК
(пакет `@cdek-it/widget`, загружается только при выборе СДЭК) и видит цену и срок по тарифу. Карта обращается к
серверу `/api/cdek` (`scripts/cdek.mjs`), ключи СДЭК есть только на сервере. Переменные сервера:

- `CDEK_CLIENT_ID`, `CDEK_CLIENT_SECRET` — ключи интеграции из личного кабинета СДЭК (раздел «Интеграция»);
- `CDEK_API_BASE` — не задавать на боевом сайте; локально `https://api.edu.cdek.ru/v2` с открытым тестовым
  аккаунтом СДЭК из его документации;
- `YANDEX_MAPS_KEY` — ключ Яндекс Карт («JavaScript API и HTTP Геокодер»), ограниченный адресом сайта.

Без любого из ключей карта не показывается: покупатель вписывает город и пункт вручную, менеджер уточняет цену.
Вес посылки пока считается по 150 г на товар плюс 100 г упаковки (веса товаров в каталоге нет).

## Аккаунты и база данных (Postgres)

Регистрация, вход и данные аккаунта (корзина, избранное, лист ожидания, черновики заказов, план приёма,
марафон) хранятся в Postgres, если серверу задан `DATABASE_URL`. API —
`apps/api/accounts.mjs`, его запускает отдельный API; сайт проксирует `/api/`:

- `GET /api/auth/me` — аккаунт и его данные, 401 без входа;
- `POST /api/auth/register`, `POST /api/auth/login` (только российская почта), `POST /api/auth/logout`;
- `PUT /api/account` — профиль (`profile`) и данные аккаунта (`data`).

Пароли — scrypt с солью; сеанс — cookie `nsp_session` (HttpOnly, SameSite=Lax, 30 дней),
в базе только SHA-256 токена. Запросы, меняющие данные, принимаются только как JSON со
своего адреса. Неудачные входы: 10 за 15 минут на адрес и логин. Таблицы создаются сами
при первом запросе. Без `DATABASE_URL` запросы аккаунтов отвечают 503, и сайт работает с
пробным аккаунтом в браузере (раздел выше).

Сайт решает по ответу `/api/auth/me` (`packages/presentation/store.tsx`): изменения данных вошедшего
уходят на сервер через 0,6 с; пока сервер не подтвердил, в браузере стоит отметка
`nsp-center:sync-dirty`, и следующая страница отправляет свою копию, иначе берёт копию
с сервера. При входе корзина и списки гостя добавляются к аккаунту; при выходе на
устройстве не остаётся ничего из аккаунта.

Локально, без установки Postgres (сервер из пакета `embedded-postgres`):

```sh
npm run db:local   # держит Postgres на 127.0.0.1:8700, данные в ~/.local/state/nsp-center/postgres;
                   # при первом запуске пишет DATABASE_URL в .env (git его не берёт)
npm run db:seed    # тестовые аккаунты anna@, ivan@, olga@ и admin@test.nsp-center.ru, пароль test2026
npm run preview    # сайт читает .env и включает аккаунты
```

Проверка — `tests/accounts.test.mjs` (поднимает временный Postgres; под root пропускается).

### Управление сайтом (администратор)

Управление сайтом — отдельный адрес `/office-k7m4q9/` (`apps/admin/admin.tsx`, API — `apps/api/site-admin.mjs`) со своим входом
для сотрудников (`/api/admin/login`, кука `nsp_staff`, сессия 12 часов). Сотрудник — отдельный аккаунт (роль
`admin`): он не входит как покупатель, а покупатель не входит в управление; личного кабинета в управлении нет.
`/office-k7m4q9/` закрыт от поиска (`noindex`, нет в карте сайта) и не хранится офлайн. Слева меню: Сводка, Заказы,
Товары, Курс у.е., Отзывы, Чат-консультант, Сотрудники:

- **Курс у.е.** — рубли = у.е. из прайса × курс; новый курс сразу меняет все цены. Курс ЦБ
  показывается для сравнения (cbr.ru, кэш на час). История — в `admin_log`.
- **Цены и наличие** товара: свои у.е. или рубли вместо расчёта, «в наличии / нет в наличии»;
  «Вернуть как в прайсе» снимает изменения.
- **Новая карточка товара** (кнопка над поиском в «Товарах»): название, артикул, раздел каталога, розничная
  цена и цена по карте в рублях, наличие (`/api/admin/new-product`, таблица `custom_products`,
  `packages/presentation/custom-product.mjs`). Карточка создаётся скрытой и сразу открывается в обычном редакторе: описание, состав,
  сертификаты и фото заполняются там же, где у всех товаров; «Показать на сайте» открывает её покупателям. Адрес —
  `/product/<название латиницей>/`; готовой HTML-страницы у неё нет, сервер отдаёт оболочку страницы с данными
  карточки, и браузер её рисует; в карте сайта она появляется, когда видна покупателям. Цена по карте, как у всех,
  уходит только через `/api/card-prices`. Цены в рублях не зависят от курса у.е. Созданную карточку можно удалить
  («Удалить карточку» с подтверждением) вместе с её описанием, фото и отзывами; товары сборки только скрываются.
- **Контент** (`apps/admin/admin-content.tsx`, `/api/admin/site-content`, таблицы `content_items` и `content_hidden`,
  правила — `packages/presentation/site-content.mjs`): «Акции» (название, условия, даты «с … по …», фото, ссылка; закончившаяся
  акция уходит со страницы сама), «Фотогалерея» (несколько фото сразу, большие снимки уменьшаются в браузере до
  2000 px, подпись), «Видеогалерея» (ссылка на ролик VK Видео, Rutube или YouTube и название; видео не хранится
  на сайте), «Журнал» (заголовок, дата, обложка, вводный абзац, текст: пустая строка — новый абзац, «## » —
  подзаголовок, «- » — список; товары из статьи), «Частые вопросы» (вопрос и ответ). Только поля с текстом,
  разметка не принимается. Добавленное идёт первым; ролики, статьи и ответы старого сайта можно скрыть и вернуть.
  Новая статья живёт по адресу `/blog/<заголовок латиницей>/`: сервер отдаёт её текст прямо в странице (для
  поисковиков) и добавляет адрес в карту сайта. С записью удаляется и её загруженное фото.
- **Скрыть с сайта / Вернуть на сайт** — кнопка над вкладками товара, действует сразу
  (`/api/admin/visibility`, таблица `product_visibility`, запись в `admin_log`). Скрытого товара нет в каталоге,
  поиске, на главной, в темах, подборе теста, плане приёма и в чате; он считается «нет в наличии». Страница
  остаётся по своему адресу и говорит, что товара нет в продаже (`noindex`). Скрытые товары собраны в
  разделе «Товары» списком «Скрыты с сайта»; выбор администратора сильнее того, что задано при сборке.
- **Оценка товара** — среднее звёзд всех отзывов с одним знаком после запятой и их число («★ 4.8 · 5 отзывов»):
  опубликованные отзывы покупателей и комментарии экспертов. У комментария эксперта 5 звёзд, пока администратор не
  поставит другую оценку (звёзды под комментарием на странице товара, `/api/admin/note-stars`); скрытые не считаются.
  Без отзывов — «Отзывов пока нет». Оценки старого сайта хранятся в данных, но не показываются.
- **Отзывы покупателей**: пишут только вошедшие (`packages/presentation/reviews.tsx`), на сайте отзыв появляется
  после «Опубликовать»; «Удалить». Комментарии экспертов на сайте не скрываются; их звёзды администратор
  меняет на странице товара.
- **Чат-консультант** — вопросы посетителей в чате сайта и ответы чата (`/api/chat-log` пишет каждый вопрос из
  `apps/web/src/assistant.tsx`, таблица `chat_log`, без имени, почты и адреса посетителя, хранится 90 дней, не больше 60
  вопросов в час с одного адреса): счётчики за сегодня, 7 и 30 дней, фильтр «Без ответа» — вопросы, на которые
  чат не смог ответить.
- **Сотрудники**: добавить по своей почте (одноразовый пароль показывается один раз) или удалить; почту
  покупателя сотруднику дать нельзя. Входы сотрудников пишутся в `admin_log`.

Сайт собирается с рублями по курсу прайса; `GET /api/site` (курс, изменения товаров, скрытые с сайта товары, скрытые
комментарии) применяется в браузере после загрузки страницы (`packages/presentation/site.ts`, кэш в
`nsp-center:site`). Разметка для поисковиков (цена в JSON-LD) обновится при следующей сборке.
Права одинаковые у всех сотрудников; роли «Владелец / Менеджер / Контент» отложены до появления второго
сотрудника. Пока в управлении работает только владелица.

Первого сотрудника создаёт `npm run admin:create -- <почта> [--name "Имя Фамилия"]` (пароль из
`ADMIN_PASSWORD` или сгенерированный, печатается один раз; пока только для локальной базы). `ADMIN_EMAILS`
больше не читается: регистрация никогда не даёт прав сотрудника. Локально есть и тестовый
`admin@test.nsp-center.ru` из `npm run db:seed`.
На dev-стенде аккаунты включатся, когда владелец инфраструктуры создаст базу Postgres в
Coolify и задаст приложению переменную `DATABASE_URL`; до этого стенд работает как раньше.

## Наличие, подтверждённое офисом NSP

`packages/catalog/source/product-stock.json` — что поставщик подтвердил позже снимка: `inStock` — артикулы в наличии,

наличия снимка: суббота до 17:30.

## Новые товары (после снимка сайта)

Товары, которых не было на старом nsp-center.ru, добавляются файлом
`packages/catalog/source/product-new/<id>.json`: название, артикул из прайса, раздел (подраздел — через «/»:
«Натуральная косметика/Уход за кожей лица и шеи», тогда товар есть в обоих), факты с этикетки
(состав, применение, противопоказания, хранение), переписанное описание и картинка в
`public/images/products/`. `scripts/new-products.mjs` добавляет их после импорта снимка:
своя страница `/product/<id>/`, цены по прайсу, первое место на первой странице раздела.
Проверки снимка (166 товаров) их не считают; у них своя проверка в `tests/build.test.mjs`.
Заменить картинку — положить файл в `public/images/products/` и поправить поле `image`.

План приёма поддерживает отдельные даты: выбор нажатием на дату под «Приём на сегодня», добавление, изменение времени и удаление относятся только к выбранному дню. Будущие дни нельзя отметить как принятые. При смене дня активируется заранее сохранённый план; если его нет, день пустой. Старый план сохраняется на своей дате. Данные хранятся в localStorage этого браузера.

## ИИ-консультант (нейросеть по ключу)

Харнесс — `apps/api/ai-agent.mjs`, адреса `/api/ai/status` и `/api/ai/ask` (их подключает `apps/api/app.mjs`).
На каждый вопрос он находит 8 фрагментов материалов врачей (поиск BM25 по темам, комментариям экспертов и,
если задан `AI_CORPUS_FILE`, по полным лекциям), отдаёт их нейросети вместе с правилами (не ставить диагнозы, не
обещать лечения, при тревожных признаках — к врачу, товары только из списка), проверяет ответ (обещания лечения →
ответ заменяется на «лучше спросить специалиста») и добавляет источники и карточки товаров. Тревожные признаки
(высокая температура, боль в груди…) до нейросети не доходят: сразу «к врачу, 103/112».

Включается переменными сервера: `YANDEX_API_KEY` (секретная часть API-ключа Yandex AI Studio) и
`YANDEX_FOLDER_ID` (каталог), модель — `YANDEX_MODEL` (по умолчанию `yandexgpt-5.1`). Без них чат отвечает
готовыми материалами, как раньше. Лимиты: `AI_DAILY_LIMIT` вопросов с адреса в день (30),
`AI_MONTHLY_LIMIT_RUB` в месяц (3000), цена 1000 токенов — `AI_PRICE_PER_1K_RUB` (0,8 ₽ — YandexGPT Pro 5.1 по тарифу AI Studio; для Lite — 0,2).
Вопросы и ответы 30 дней хранятся в `ai_log` (без аккаунта, хеш адреса) и видны сотрудникам в разделе «Чат-консультант».
Полные лекции — по желанию: `node scripts/build-lecture-corpus.mjs` пишет фрагменты вне репозитория, путь к файлу —
`AI_CORPUS_FILE`. Локальная проверка без ключа — `AI_PROVIDER=mock` (ответ из лучшего фрагмента). Проверка —
`tests/ai-agent.test.mjs`.

Что он отвечает:

- советы по самочувствию из лекций врачей: уточняющий вопрос, затем «Вам может подойти «…»» с разделами
  «Зачем это вам / Чем полезен / Как принимать / По возрасту / Не подходит», «Источник: врач, лекция» и
  «БАД не является лекарственным средством»;
- вопросы магазина (`shopAnswer`): цена и наличие товара, с чем сочетается (пары из лекций), как принимать,
  состав и аллергены, противопоказания, сравнение двух товаров, доставка с ценами, как заказать, где заказ,
  оплата, возврат, сертификаты и «Честный знак», срок годности, часы работы, контакты, акции, подарки, опт,
  партнёрство и баллы PV, «ты бот?»;
- уточнения про только что названный товар («а сколько он стоит?»), опечатки и разговорные названия
  («хлорафил», «омего три», «аг икс», «витамин д3»);
- беременность, кормление, дети, лекарства, давление, хронические болезни, «вылечит ли» — без подбора товара,
  сначала врач; тревожные признаки — отдельная карточка с кнопками «Позвонить 103» и «112».

Связь с человеком — только звонок и почта (WhatsApp в чате не предлагается).
Вид: подсказки столбиком под ответом, «Подробнее о продукте» — текстом со стрелкой, время у последнего
сообщения серии; строка ввода и «Помощник не заменяет консультацию врача» — в конце переписки (уходят вверх
вместе с ней); большой ответ открывается так, что видно вопрос и начало ответа. Переписка живёт во вкладке.

Проверка ответов — банк из 87 типовых вопросов покупателей (исследование 2026-11-10), прогон в холсте.


## WebP: фотографии, товары и баннеры

Правило закреплено в `AGENTS.md`: растровые изображения контента публикуются в
WebP. Исходники снимка и утверждённые изображения сохраняются для восстановления.
SVG-иконки и маски, обязательные PNG-иконки приложения не преобразуются.

`npm run images:webp` создаёт копии в `public/webp/` из JPG/PNG/GIF в
`public/images`, `public/media`, `public/prototype`. Размеры сохраняются,
ориентация нормализуется, прозрачность поддерживается. Качество WebP — 90,
качество альфа-канала — 100. Манифест хранит хеш исходника и параметры конвертации;
повторная сборка переиспользует готовые файлы. Выходные файлы воспроизводимы и
не добавляются в git. Требуется установленная через npm зависимость `sharp`.

тот же механизм `packages/domain/webp.mjs`. Пример адреса:
`/images/photo.jpg` → `/webp/images/photo.webp`. Первичные импортированные
данные не переписываются: проверка сохранности исходников остаётся побайтовой.

Админка принимает JPG/PNG/WebP; API проверяет реальное содержимое и сохраняет

потерь. Существующие загруженные JPG/PNG выдаются как WebP с адресом
`/api/files/<id>.webp`; исходные записи БД сохраняются. Суффикс отделяет новую
версию от ранее закешированного оригинала. Старые ссылки продолжают работать.

Проверки: `tests/webp.test.mjs`, загрузки/невалидные файлы/старые записи в
`tests/accounts.test.mjs`, WebP через отдельную админку в интеграционном тесте.
CI также проверяет Content-Type файлов в контейнерах web и admin.

### Email и контактный телефон аккаунта

Вход покупателя и сотрудника использует email и пароль в отдельных областях.
Одна почта может принадлежать одному покупателю и одному сотруднику (включая
отключённого сотрудника). Создание сотрудника не повышает права покупателя.
Контактный телефон может повторяться; по нему не выполняются вход,
объединение аккаунтов или перенос карты и баллов. Индекс
users_email_scope_key сохраняет уникальность email без учёта регистра внутри
каждой области. SCHEMA автоматически заменяет прежние глобальные индексы
email и телефона при запуске API; записи пользователей сохраняются.
Восстановление пароля пока демонстрационное; при подключении почты поиск и
токен сброса должны относиться к конкретному аккаунту и области входа.

### Сохранение и просмотр заказа в PostgreSQL (18 ноября 2026)

`POST /api/orders` сохраняет неоплаченный заказ, строки `order_items` и событие
`created` в `order_events` одной транзакцией. Миграция `apps/api/order-schema.mjs`
переносит старые JSON-товары в строки, проверяет суммы и убирает дублирующие
`shop_orders.items` и рублёвое `shop_orders.total`. До применения к локальной базе
сделан полный dump в `~/.local/state/nsp-center/backups/` (доступ только владельцу).
Миграция повторяема; при несовместимых данных завершается ошибкой без частичного
переноса. Старые заказы не получают выдуманную историю оформления.

Денежные поля базы — целые копейки. `subtotal_kopecks` — стоимость товаров после
скидки, `discount_kopecks` — разница с розничной стоимостью, `total_kopecks` —
товары после скидки плюс известная доставка. Отложенные constraint triggers
проверяют при commit наличие товаров, сумму строк, скидку и итог. Несогласованная
запись откатывается, в том числе при прямом SQL-изменении. Количество и цена строки
также проверяются CHECK-ограничениями. При будущих правках состава сначала нужно
блокировать строку заказа и менять строки/итоги в одной транзакции.

`order_read` — представление для чтения: собирает список товаров и рублёвую сумму
из канонических данных. Оно не хранит вторую копию. API сохраняет прежний формат
цен в рублях для совместимости сайта и админки; PostgreSQL хранит копейки.

Бэкенд проверяет цены, наличие и право на цену по карте по текущему аккаунту.
UUID операции и хеш нормализованного запроса защищают от повторного оформления.
Тот же запрос возвращает прежний заказ, даже после изменения каталога; изменение
запроса с прежним UUID даёт 409. Ключ, хеш формы и случайный ключ гостевого доступа
временно сохраняются во вкладке, чтобы пережить потерю ответа. После успешного
оформления выбранные товары убираются из корзины и открывается `/order/?id=…`.

Постоянная страница получает сведения через `GET /api/orders/:id`. Вошедшему
покупателю доступен только его заказ. Гостю выдаётся секретная ссылка с 256-битным
ключом в URL-фрагменте `#access=…`; он не попадает в HTTP URL и referrer. База хранит
только SHA-256 ключа. Чтение требует заголовок Authorization; одна лишь почта или
номер заказа доступа не дают. Ключ даёт только чтение конкретного гостевого заказа,
не доступ к аккаунту. Для повторного открытия гость сохраняет ссылку; письма пока
не отправляются. После утраты ссылки автоматического восстановления доступа нет.
Страница закрыта от индексации, имеет no-store и no-referrer, не кешируется PWA.
Ответы API не содержат служебных комментариев, причин исправлений и ключей доступа.

При оформлении сохраняется адрес самовывоза из серверной конфигурации. Старые
заказы без снимка получают текущий адрес с пометкой `pickupAddressSource=migration`
и временем переноса: точный исторический адрес для них заново не выдумывается.
Последующие изменения адреса магазина не переписывают снимки заказов.

Правила статусов общие для API и админки (`packages/domain/order-status.mjs`):
новый → собирается → отправлен → получен; самовывоз: собирается → получен.
До отправки возможна отмена с причиной. Завершённый и отменённый заказы не имеют
обычных переходов. Ошибочный статус сотрудник исправляет отдельным режимом,
с обязательной причиной от 5 до 1000 знаков. Сохраняются предыдущий/новый статусы,
сотрудник, время, причина и признак исправления. Старые события не переписываются.
Изменение служебного комментария — отдельное событие. Проверка версии заказа
защищает от одновременной перезаписи двумя сотрудниками.

ЮKassa, платежи, чеки, письма, резервирование и возвраты пока не подключены.
Статус оплаты — `not_connected`. СДЭК требует серверного расчёта:
`delivery_kopecks = NULL`, `priceStatus = requires_quote`; показанная сумма такого
заказа включает только товары. Цена из браузера не считается подтверждённым тарифом.

Проверки: `tests/order-checkout.test.mjs` использует временный PostgreSQL и проверяет
повторы, цены, доступ владельца/гостя, откат при сбое, суммы, миграцию старого заказа,
сохранность адреса, историю и исправления. `tests/order-status-rules.test.mjs`
проверяет разрешённые этапы. Обязательный общий прогон: `npm run check`.


## Обновления базы, права и резервные копии

Структуру базы меняет только `npm run db:migrate`. Пронумерованные SQL-файлы
находятся в `apps/api/database/migrations/`; применённые версии и контрольные
суммы — в `schema_migrations`. Уже применённый файл не редактируют: добавляют
следующий. Все новые миграции и синхронизация каталога проходят в одной
транзакции с блокировкой от параллельного запуска. Перед изменением рабочей
локальной базы выполняют `npm run db:backup`.

После изменения исходного каталога сначала `npm run content:catalog`, затем
`npm run db:migrate`: это обновляет общий реестр идентификаторов `products`
и базу знаний. Удалённые товары остаются в реестре с датой архивирования;
название и цена в старом заказе сохраняются в `order_items`. Каталожные тексты
и исходные цены по-прежнему авторские файлы, а не вторая редактируемая копия в БД.

`npm run db:secure` создаёт локальную роль `nsp_app` и меняет подключение
в `.env`. Полные права сохраняются отдельно в
`~/.config/nsp-center/database-admin.env` (режим 0600); API этот файл не читает.
Повторный запуск меняет пароль приложения, после него нужно перезапустить API.
У приложения нет прав создавать/менять таблицы, обновлять миграции, удалять
заказы или переписывать историю; представление `order_read` доступно только
для чтения. Работа сайта, админки и оформление заказов проверяются с этими правами.
Для внешней среды управление получает `DATABASE_ADMIN_URL`, API — отдельный
`DATABASE_URL`. Перед запуском новой версии API выполняют миграции отдельным
процессом с административным подключением; автоматически из запросов они не идут.
В образе API команда: `node apps/api/database/cli.mjs` (секрет владельца дают
только этому одноразовому процессу). Этот этап не публикует изменения на стенд.

`npm run db:backup` делает копию и восстанавливает её в отдельную временную
базу. Сравниваются количество и отпечаток строк каждой таблицы, дополнительно
проверяются суммы заказов. Только после успешного восстановления обновляется
`latest.json`. Исходная база не заменяется; удаляется лишь временная проверочная
база. Копии и их манифесты находятся в `~/.local/state/nsp-center/backups/`,
каталог доступен только владельцу (0700), файлы — 0600. Старые копии автоматически
не удаляются. Это локальные копии на том же диске: от потери компьютера они не
защищают, внешнее хранилище пока не подключено.

Для восстановления нужны `pg_dump` и `pg_restore` PostgreSQL 18: `PG_BIN_DIR`
задаёт каталог; на этом Mac используются инструменты установленного pgAdmin.
В CI устанавливается `postgresql-client-18` из
[официального репозитория PostgreSQL](https://www.postgresql.org/download/linux/ubuntu/).
`NSP_TEST_BACKUP=1 npm run check` включает восстановление временной тестовой базы;
без переменной этот дополнительный тест явно пропускается.

На macOS `npm run db:backup:install` устанавливает фоновое расписание
`com.wellwon.nsp-center.database-backup` после карточки системного действия
Factory (`cv admin intent`). Каждый час оно запускает `scripts/backup-db.mjs --due`:
если последней проверенной копии больше суток, создаёт новую. Проверка также
запускается при входе в macOS; после сна — при следующем запуске расписания.
База должна быть запущена, иначе попытка завершится ошибкой и повторится через час.
Журнал: `~/.local/state/nsp-center/database-backup.log`.
Статус: `launchctl print gui/$(id -u)/com.wellwon.nsp-center.database-backup`.
Команда установки не перезаписывает существующее расписание. Для ручного режима
без автозапуска есть `npm run db:backup:watch`, он работает только пока жив процесс.


### Дополнительная защита заказов и проверка восстановления

Миграция `004_order_guards.sql` проверяет цены внутри `custom_products.data`:
розничная — положительное целое число рублей до 10 миллионов, цена по карте —
положительное целое меньше розничной либо отсутствует. Строка вместо числа,
отрицательная цена и дробные рубли отклоняются самой базой, как и в редакторе.

У `nsp_app` нет прямого изменения статуса, контактов, адреса, сумм или владельца
заказа. Узкое право на `updated_at` нужно для блокировки строки при оформлении;
триггер запрещает использовать его для прямой записи. Смена статуса и комментария
проходит через `change_order`: проверяет действующего сотрудника, версию заказа,
переход статуса и причину отмены/исправления, затем вместе сохраняет заказ и историю.
В функцию передаётся сотрудник из проверенной сервером сессии, а не из тела запроса.
База доверяет API в установлении личности сотрудника; это не отдельная авторизация
покупателя на уровне PostgreSQL. Функция не принимает цены, адрес или владельца.
Прямое добавление поддельных событий и товаров после оформления запрещено.
Владелец базы сохраняет административные права для осознанного обслуживания.

**По решению владельца 18 ноября 2026 года расписание резервных копий отключено**
через `launchctl disable` и `bootout`; существующие копии не удалены. Облако,
внешняя копия и уведомления об ошибках копирования отложены до возобновления этой
работы. Не включать расписание и не делать новую копию рабочей базы без нового
поручения. Описанные выше команды остаются инструментами для будущего использования.
Для подтверждённых записей включены `fsync`, `full_page_writes` и
`synchronous_commit`. Это защита от сбоев, а не замена копии при потере диска.

Восстановление на чистой установке проверяет `tests/recovery.test.mjs`:
две временные установки PostgreSQL с разными владельцами, искусственные аккаунты
и заказы, восстановление всех таблиц, создание роли приложения, вход через сайт,
просмотр старого заказа, изменение статуса и новый заказ. Затем тест аварийно
останавливает только временный PostgreSQL (SIGQUIT) и сверяет данные после запуска.
Это моделирование чистой установки и сбоя процесса на этом Mac, не испытание
физической поломки ноутбука. Реальная база и её копии в тестах не используются.

Для будущего аварийного восстановления из проверенной копии:

1. Получить исходники соответствующей версии проекта, установить зависимости
   (`npm ci`) и собрать сайт (`npm run build`). Поднять чистую PostgreSQL 18 и
   создать пустую целевую базу; в кластере ещё не должно быть роли `nsp_app`.
2. Предоставить `.dump` и его соседний `.dump.json`. Задать административное
   подключение к пустой базе через `RESTORE_DATABASE_URL` в приватном окружении,
   не вставляя пароль в переписку, историю команд или репозиторий.
3. Выполнить `npm run db:restore -- /путь/backup.dump`. Скрипт проверяет SHA-256,
   отказывается перезаписывать непустую базу или существующую роль, восстанавливает
   данные и ограничения, сверяет отпечатки таблиц и суммы заказов, создаёт `nsp_app`
   с новым паролем и выдаёт права. Подключение сохраняется в `.env.recovered` с
   правами 0600; существующий файл не перезаписывается. Альтернативный путь задаёт
   `RESTORE_APP_ENV`. В журнал пароль не выводится.
4. Подключить API с этими новыми реквизитами по обычной инструкции запуска,
   проверить вход покупателя/сотрудника и старые заказы. Для внешних интеграций
   нужны отдельно восстановленные секреты: они не входят в копию базы.

Восстановление не обновляет схему автоматически: версия кода должна соответствовать
копии. Если копия старая, сначала используют соответствующую версию, затем отдельно
планируют миграции. Ошибка проверки не превращается в автоматическое стирание
целевой базы; она остаётся для диагностики. Повторять восстановление следует в
новую пустую базу. Рабочее подключение API никогда не направляют на неё до проверки.

Локальные страницы восстановления пароля (`/__preview/password-recovery/`) собираются автоматически в `npm run build:web` и поэтому также в `npm run check`. Кнопка «Забыли пароль» на localhost не должна вести на исчезающий после пересборки файл. Это демонстрационные экраны: отправка письма и серверная смена пароля ещё не подключены.
